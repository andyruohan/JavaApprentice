### 第 1 题：Redis 缓存穿透

**题目：** 以下哪个描述对缓存穿透的理解是正确的？

A. 缓存数据太多导致数据结构崩塌而导致大量请求都去查询数据库  
B. 缓存数据太多导致内存不够，清理缓存导致大量请求都去查询数据库  
C. 大量查询请求在缓存没有命中，导致大量请求都去查询数据库  
D. 大量缓存同时失效导致大量请求都去查询数据库

**我的答案：C**

**我的理解：** A、B 均不是缓存穿透的典型描述；D 属于缓存雪崩。

**参考答案：C**

**解析：**

缓存穿透通常指请求查询的数据既不存在于缓存中，也不存在于数据库中，导致请求持续穿过缓存访问数据库。

需要区分以下三种情况：

| 类型 | 核心特征 | 典型场景 |
|---|---|---|
| 缓存穿透 | 查询不存在的数据 | 反复查询不存在的用户 ID |
| 缓存击穿 | 热点 Key 失效 | 热门商品缓存突然过期 |
| 缓存雪崩 | 大量 Key 同时失效或缓存服务故障 | 大量缓存同时过期 |

注意：C 只是缓存穿透的简化描述。普通缓存未命中并不一定属于缓存穿透。

**知识记忆要点：**

- 穿透：数据通常根本不存在。
- 击穿：单个热点 Key 失效。
- 雪崩：大量 Key 同时失效。
- 穿透的常见解决方案：布隆过滤器、缓存空值、参数校验和限流。

### 第 2 题：Kafka Controller 故障恢复

**题目：** Kafka 在高可用环境中使用 ZooKeeper 管理集群状态。当 Kafka 集群中的控制器节点故障时，以下哪个过程会在 ZooKeeper 的帮助下触发？

A. Kafka 所有 Broker 自动重启，重新加入集群  
B. 由 ZooKeeper 重新选举一个新的控制器节点来承担控制器角色  
C. ZooKeeper 将所有现有分区的领导者切换到不同 Broker  
D. Kafka 生产者和消费者立即停止所有消息操作，等待手动恢复控制器

**我的答案：B**

**我的理解：** A、D 与控制器故障恢复无关。C 不确定是否正确，但题目明确强调 Controller 故障。

**参考答案：B**

**解析：**

在旧版 ZooKeeper 模式中，Kafka Controller 是由某个 Broker 承担的特殊控制角色。

当 Controller 故障时，其他 Broker 在 ZooKeeper 协调下竞争成为新的 Controller。

需要区分两个概念：

1. Controller 选举：选择负责集群管理与元数据协调的控制器。
2. Partition Leader 选举：选择某个分区负责读写请求的 Leader 副本。

Controller 故障并不代表所有 Partition Leader 都需要重新选举，因此 C 错误。

**知识记忆要点：**

- Controller 负责集群管理和分区 Leader 选举协调。
- ZooKeeper 模式通过临时节点、Watch 等机制协调 Controller 选举。
- Broker 故障与 Controller 故障不完全相同。
- Kafka 4.0 起移除了 ZooKeeper 模式，使用 KRaft Controller Quorum。

### 第 3 题：Redis 基本数据类型

**题目：** 常用中间件 Redis 的基本数据类型不包括？

A. Int  
B. List  
C. String  
D. Hash

**我的答案：A**

**我的理解：** Int 不是 Redis 的基本数据类型，但 String 可以采用 int 内部编码存储。

**参考答案：A**

**解析：**

Redis 五种经典基础数据类型：

1. String
2. List
3. Hash
4. Set
5. Sorted Set（ZSet）

String 的常见内部编码包括：

| 内部编码 | 说明 |
|---|---|
| int | 使用整数形式存储 |
| embstr | 较短字符串的紧凑存储 |
| raw | 一般字符串存储 |

**知识记忆要点：**

- 数据类型和内部编码不是一个概念。
- Redis String 可以使用 int 编码。
- int 并不是独立的 Redis 基本数据类型。
- 不同 Redis 版本的数据类型内部编码可能不同。

### 第 4 题：分布式 SQL 优化

**题目：** 假设我们要对分布式 SQL 进行优化，下列方法无效的是？

A. 可以使用 UNION ALL 的情况下，不要使用 UNION  
B. 两表 JOIN 时，条件字段尽量放在 WHERE 里面  
C. 避免关联字段分布倾斜  
D. 大表 JOIN 小表时，可以考虑 Map-side Join

**我的答案：B**

**我的原理解：** 应尽量将 JOIN 条件放在 ON 中。

**参考答案：B**

**解析与纠正：**

B 不属于可靠的通用性能优化手段。

对于 INNER JOIN，连接条件写在 ON 或 WHERE 中，通常具有相同语义，优化器也可能生成相同执行计划。

例如：

```sql
SELECT *
FROM a
JOIN b ON a.id = b.id;
```

与：

```sql
SELECT *
FROM a
JOIN b ON 1 = 1
WHERE a.id = b.id;
```

通常可以等价优化。

但对于 LEFT JOIN 等外连接，ON 与 WHERE 可能改变查询语义，不可随意替换。

真正重要的优化手段：

- UNION ALL 避免不必要的去重操作。
- 避免 JOIN 字段发生数据倾斜。
- 利用 Map-side Join 或 Broadcast Join 减少跨节点数据交换。
- 尽可能利用谓词下推、索引及合适的连接策略。

**知识记忆要点：**

ON 和 WHERE 不能简单按性能高低排序；应结合 JOIN 类型、SQL 语义及执行计划判断。

### 第 5 题：MyBatis 一级缓存

**题目：** 对于 MyBatis 一级缓存说法错误的是？

A. 同一个 SqlSession 只能开启一级缓存  
B. 不同 SqlSession，即使同一个 Mapper 也会到数据库中进行不同查询，即不同 SqlSession 一级缓存是无效的  
C. 参数与 SQL 相同，且缓存未被刷新等情况下，使用同一个 SqlSession 调用同一个 Mapper 方法，会读取缓存结果  
D. 默认没有配置的情况下，针对同一个 SqlSession 只会开启一级缓存

**我的答案：A**

**我的理解：** 同一个 SqlSession 也可以使用二级缓存，因此不能说只能开启一级缓存。

**参考答案：A（题目存在歧义）**

**解析：**

MyBatis 缓存分为一级缓存和二级缓存。

| 对比项 | 一级缓存 | 二级缓存 |
|---|---|---|
| 作用范围 | SqlSession | Mapper Namespace |
| 默认状态 | 默认启用 | 全局开关默认开启，但 Mapper 通常需要配置 |
| 是否跨 Session | 不可以 | 可以 |
| 主要用途 | 减少同一会话重复查询 | 复用不同会话的查询结果 |

一级缓存和二级缓存可以同时参与查询。

MyBatis 查询时通常先检查二级缓存，再进入 Executor 使用一级缓存；因此需要注意：“缓存命中顺序”不能简单理解为一定先检查一级缓存再检查二级缓存。

A 说只能开启一级缓存，如果理解为同一个 SqlSession 不可能使用二级缓存，则错误。

但如果仅表示一级缓存属于 SqlSession 级别，则有一定合理性。

B 强调不同 SqlSession 不能共享一级缓存，这一点正确。但如果由此推导“不同 SqlSession 一定访问数据库”，则不正确，因为可能命中二级缓存。

**知识记忆要点：**

- 一级缓存的默认作用域是 SESSION。
- 不同 SqlSession 不共享一级缓存。
- 二级缓存可以跨 SqlSession。
- 执行更新、提交、回滚、关闭等操作会影响一级缓存。
- 同一个 Mapper Namespace 可以配置二级缓存。
- 本题 A、B 均有表述不严谨之处，不宜死记单选答案。

### 第 6 题：Kafka 与 ZooKeeper 元数据

**题目：** 以下哪项不属于 ZooKeeper 管理的 Kafka 元数据？

A. Controller 选举信息，包括当前 Controller Broker ID  
B. Broker 注册信息，包括 Broker ID 和网络地址  
C. 消费者组的 Offset 位移信息  
D. Topic 配置信息，包括分区数量和副本分配

**我的答案：C**

**我的理解：** 消费者组 Offset 不属于 ZooKeeper 当前主要维护的元数据。

**参考答案：C（适用于较新版 ZooKeeper 模式）**

**解析：**

在较新版的 ZooKeeper 模式 Kafka 中：

- ZooKeeper 参与 Controller 选举协调。
- ZooKeeper 保存 Broker 注册信息等集群元数据。
- Topic 和 Partition 的相关元数据由 ZooKeeper 模式下的控制机制管理。
- 消费者组 Offset 通常存储于 Kafka 内部 Topic `__consumer_offsets`。

Offset 提交流程可以简化为：

```text
Consumer
    ↓
Group Coordinator（Broker）
    ↓
__consumer_offsets
```

历史上，Kafka 早期消费者实现曾支持将 Offset 保存到 ZooKeeper，因此 C 是有版本前提的答案。

**知识记忆要点：**

- ZooKeeper 主要承担旧版 Kafka 集群协调与元数据管理。
- Consumer Group Offset 通常保存在 `__consumer_offsets`。
- Kafka 消息实际存储在 Broker。
- Kafka 4.0 起采用 KRaft 模式，不再依赖 ZooKeeper。

### 第 7 题：Eureka 自我保护机制

**题目：** 关于 Eureka 自我保护机制，说法错误的是？

A. 固定时间内大量实例被注销，可能严重威胁微服务架构可用性，因此 Eureka 提供自我保护机制  
B. 自我保护模式是针对网络异常波动的保护措施，可以提升 Eureka 集群稳定性  
C. Eureka Server 统计心跳失败比例在 15 分钟内是否低于 85%，低于 85% 就进入自我保护机制  
D. 网络故障可能造成服务实例虽然正常运行，却被注册中心错误注销

**我的原答案：未确定**

**我的疑问：** A、B、D 均正确，C 为什么错误？

**最终参考答案：C**

**关键错误：**

原题 C 将“心跳失败率”和“85% 阈值”错误关联。

应该是：

- 心跳续约达成率低于约 85%，可能触发自我保护条件。
- 等价地说，心跳缺失比例超过约 15%。
- 不是心跳失败比例低于 85%。

此外，“15 分钟”并非统计最近心跳成功率的窗口，而是默认预期续约阈值的周期性更新间隔。

#### 修正后的 C 选项

**C. Eureka Server 默认每隔 15 分钟周期性更新预期心跳续约次数阈值，并根据最近 1 分钟实际收到的心跳续约次数判断是否允许正常剔除过期实例。当实际续约次数未超过按照预期续约次数的 85% 计算得到的阈值时，Eureka 在启用自我保护的情况下暂停正常的实例过期剔除。**

需要强调：15 分钟是默认的周期更新间隔，不代表阈值只会每 15 分钟变化一次，实例注册、下线等操作也可能影响预期续约数量。

#### 阈值计算示例

假设 Eureka 中存在 100 个服务实例，每个实例默认每 30 秒发送一次心跳。

每分钟预期心跳次数：

`100 × 2 = 200`

自我保护阈值：

`200 × 85% = 170`

| 实际每分钟收到心跳 | 续约达成率 | 判断 |
|---|---|---|
| 190 | 95% | 高于阈值，允许正常过期剔除 |
| 170 | 85% | 未超过阈值，满足暂停剔除的阈值条件 |
| 120 | 60% | 低于阈值，满足暂停剔除的阈值条件 |
| 40 | 20% | 低于阈值，满足暂停剔除的阈值条件 |

此处是对默认行为的简化计算，实际还取决于 Eureka 版本、注册实例数量及相关配置。

#### 为什么每 15 分钟更新阈值？

Eureka 集群中的服务实例数量会随业务扩容、缩容、正常上线和下线变化。

例如：

| 实例数量 | 每分钟预期续约 | 85% 阈值 |
|---|---|---|
| 100 | 200 | 170 |
| 150 | 300 | 255 |
| 50 | 100 | 85 |

因此，85% 这个比例通常固定，但对应的续约次数阈值可能变化。

为了避免网络异常导致大量实例看似消失时，Eureka 错误地降低阈值，周期性更新还需要考虑自我保护状态及实例数量变化条件，并不是无条件降低阈值。

**知识记忆要点：**

- 85%：默认续约阈值比例。
- 最近 1 分钟：实际收到的心跳续约次数统计窗口。
- 15 分钟：默认周期性更新预期续约阈值的间隔。
- 自我保护主要防止网络问题导致大规模错误剔除实例。
- Eureka 自我保护不是主动恢复故障实例，而是暂停正常的实例过期剔除。
- 暂停剔除也可能导致注册表中暂时保留不可用实例，这是 AP 倾向设计中的典型权衡。

## 四、后续需要重点复习

**第一优先级：Eureka 自我保护机制**

需要能解释续约阈值计算、阈值更新、自我保护触发条件，以及为何网络分区时不立即剔除大量实例。

**第三优先级：Kafka 元数据与高可用**

需要区分 Controller 选举、Partition Leader 选举、Broker 副本同步，以及 ZooKeeper 与 KRaft 模式的区别。
