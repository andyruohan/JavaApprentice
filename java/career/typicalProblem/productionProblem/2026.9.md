**一、版本发布顺序错误导致日终应用报错**

**问题描述**

某日终应用次日凌晨执行任务出现异常，当晚与其存在依赖的联机应用接口新增了非空字段，日终旧版本调用时未传入该字段导致报错。最终通过回退灰度版本，并重跑日终任务解决。

**问题根因**

本次投产包含联机和日终两套应用改造，且存在依赖关系。

1. UAT 阶段确定灰度方案时，未识别出发布的依赖关系（日终应用应在联机应用前发布，或在联机灰度发布当天同步发布），也未在 UAT 添加日终灰度案例覆盖。
2. 日终应用在调用联机应用接口加工失败时无告警通知，导致问题未被及时发现。

**经验分享**

1. 做好版本依赖分析。梳理上下游依赖及接口变更，明确发布顺序，评审灰度与回退方案，并在测试环境验证，补充日终灰度测试案例。
2. 完善版本兼容措施。对影响上下游的变更逻辑增加开关，作为版本不同步时的兜底措施，降低灰度期间新旧版本不兼容的风险。
3. 加强日终异常监控。日终程序处理失败时应及时中断并发出告警，便于值班人员快速发现和介入，减少问题发现延迟及后续处理成本。

**二、使用 WHERE + ORDER BY 筛选数据出现慢 SQL**

**问题描述**

G01 从 Oracle 切换至 TDSQL 后，某 SQL 使用 ORDER BY + LIMIT 查询。虽然 WHERE 条件字段已建立索引，执行时仍发生全表扫描，查询耗时超过 1 分钟。（注：该表数据量为 800 余万行。）

**问题根因**

TDSQL 默认开启 prefer_ordering_index 属性，优化器倾向于选择能够避免排序的索引，即使该索引的过滤效率较低。在 ORDER BY + LIMIT 场景下，这种倾向更明显，可能因扫描大量数据而导致查询变慢。

例如，假设 orders 表中分别存在 status 字段索引 idx_status 和 create_time 字段索引 idx_create_time，执行以下 SQL：

```sql
SELECT * FROM orders WHERE status = 'paid' ORDER BY create_time LIMIT 10;
```

不同 prefer_ordering_index 属性配置下，优化器的索引选择倾向及执行效果如下：

| 配置 | 索引选择倾向 | 过滤与排序效果 | 适用场景说明 |
|---|---|---|---|
| OFF | 更倾向于选择 idx_status | 先通过索引筛选出 status = 'paid' 的记录，再对结果集按 create_time 排序，取前 10 条。 | 符合条件的记录较少时，通常效率较高；符合条件的记录较多时，排序开销可能增大。 |
| ON | 更倾向于选择 idx_create_time | 按时间索引顺序扫描，回表检查 status，找到 10 条符合条件的记录后停止，无需额外排序。 | 符合条件的记录在扫描起点附近较密集时，可快速返回；较稀疏时，可能扫描大量索引条目并频繁回表，导致查询变慢。 |

**经验分享**

“免排序”不一定意味着执行效率更高，应结合过滤条件的选择性、数据在排序索引中的分布，以及统计信息和优化器成本估算综合判断。使用 ORDER BY 时，WHERE 条件应有效筛选结果集，通常控制在 500 条以内。鉴于行内 TDSQL 默认开启 prefer_ordering_index，建议结合实际业务场景和执行计划，必要时指定合适的索引，避免因过滤效率低、扫描数据过多导致慢 SQL。

**三、数仓典型数据同步异常案例**

**问题描述**

案例一：分库数据迁移后重复。源系统将正式库部分数据迁移至灰度库后，同一业务记录同时存在于多个分库，入仓时触发主键重复校验。

案例二：新旧表数据主键冲突。源系统迁移旧库当前表数据后，清理了旧当前表中的已迁移数据，但保留了旧历史表中的冲突记录，导致新库当前表与旧库历史表入仓时主键冲突。

案例三：灰度版本不同步引发日终异常。上下游依赖应用未同步发布，导致日终异常，需要回退灰度版本并重试。

**问题根因**

案例一：迁移方案未考虑共享记录跨库重复。部分客户迁移后，原本位于同一分库的共享业务记录同时存在于原分库和灰度库，前期未评估其对下数规则的影响。

案例二：去重方案未验证生产数据。因排期调整，去重由数仓开发改为源系统保障，但遗漏了当前表与历史表已有的主键冲突，数仓也未配置去重逻辑，导致校验失败。

案例三：灰度期间上下游版本不同步，导致日终异常；处理步骤相互耦合，未兼容后续步骤重试，存在覆盖已有数据的风险。

**经验分享**

1. 将数仓同步纳入生产变更影响评估。数仓异常同样可能引发重大生产问题，应重视下数规则、数据合并及主键校验逻辑的严谨性。
2. 扩大试运行验证范围。数仓上线初期应尽量覆盖跨库迁移、新旧表合并、灰度切换、回退及重跑等场景，验证数据完整性、唯一性和处理结果的一致性。
3. 完善灰度发布与重试机制。明确上下游应用的发布依赖，保证版本兼容；梳理日终步骤之间的耦合关系，确保相关步骤兼容后续步骤重试，避免重复执行覆盖已有数据。
