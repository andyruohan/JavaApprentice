# IPv6 迁移遗漏 Nginx 监听配置导致页面 502

## 问题描述

某前端服务单元从 IPv4 区迁移至 IPv6 区后，客户访问其转发的下游页面出现 502 Bad Gateway，故障持续 8 分钟。因无有效监控告警，最终由人工报障发现，经流量回切恢复。

## 问题根因

迁移后域名变为 IPv4/IPv6 双栈，客户端 IPv4 源地址被强制转换为 IPv6，而新环境 Nginx 遗漏了 IPv6 端口监听配置，导致路由请求容器失败。
深层原因包括：
1. 变更影响范围评估不足，未识别该服务单元还承接了低频功能的流量转发，误判为无流量而放弃灰度发布；
2. 变更后验证不到位，页面报错被误认为正常权限控制而未深究；
3. 低流量应用监控告警阈值失效，故障无法主动发现。

## 总结与改进措施

1. IPv6 迁移投产时，Checklist 需重点检查 Nginx 双栈监听配置；
2. 变更前全面梳理服务单元的上下游流量依赖，低频流量应用同样需纳入验证与灰度范围；
3. 增强监控能力：在最外层 Nginx 增加 502 报错监控，并为低流量应用配置工作时间段个性化流量告警，实现故障主动发现。


# Kafka 配置变更导致异步消息处理中断

## 问题描述

某业务异步自动应答功能未正常触发，异步任务持续处于待执行状态。经排查确认，问题源于 Kafka 新配置错误导致异步消息处理中断。完成 Kafka 配置更新并重启应用后，系统通过自动重试机制成功处理，业务恢复正常。

## 问题根因

异步自动应答的 Kafka topic 在代码中通过枚举值硬编码为原 topic 名称，未读取数据表配置。而新申请的 Kafka 资源，topic 名称与原 topic 名称不一致，导致消息推送失败。测试环境因 topic 名称未调整过未暴露问题；生产环境灰度验证不足，未分阶段重启验证。

复盘总结：配置变更管理不完善，测试与生产环境配置差异未识别；灰度验证不足，验证手段单一，仅验证中间件连通性未结合业务场景。

## 总结与改进措施

1. 建立配置变更记录机制，开发阶段横向对比各环境差异并双人复核；灰度阶段分别评估联机、异步、定时影响及回退手段，逐一验证；全量投产后回顾配置清单确认无遗漏。
2. 完善监控与兜底机制：新增单条消息超时监控，第一时间感知异常；Kafka 异常时自动切换本地线程池处理，提高容错能力。
3. 移除 Kafka 中间件：逐步将异步任务替换为线程池处理，降低中间件配置依赖风险。


# 灰度发布顺序有误导致接口报错

## 问题描述

某应用后端灰度发布后，前端灰度实例上与本次上线相关的接口出现报错。经排查确认为灰度发布顺序兼容问题，随即对灰度实例进行隔离，业务恢复正常，待前端全量发布后再解除隔离并完成全量。

## 问题根因

1. 开发未按投产方案要求兼容前后端新旧版本的不同发布顺序，自测也未覆盖该场景；
2. 测试环境按固定顺序（先发后端再发前端、或先发前端再发后端）依次验证，未覆盖前后端版本交叉组合的场景；
3. 新增必传字段的取值方式未做防御性处理，未传即抛异常而非降级取默认值。

## 总结与改进措施

1. 前后端联合投产的变更，投产 checklist 中需明确列出所有发布顺序组合（后端先发/前端先发/灰度期间交叉），逐项确认接口兼容性并安排对应验证。
2. 新增请求字段时，后端取值统一采用防御性方式：先用 getDtoCount 预判再取值，或使用 getDtoOrElse 提供默认值，禁止直接 get 导致未传时抛异常。
3. 测试用例设计需覆盖前后端版本不一致的中间态场景，尤其是灰度发布窗口期内新旧版本并存的请求组合。
